## 0. ⚠️ YESTERDAY'S INCIDENT + RE-DEPLOY PREREQUISITES (read first)

The 2026-08-12 14:24 deploy (v26.908) caused a **~5h prod outage** (219 timeouts / 8 users): a latent trap
(`planner.category_sales_summary` was a plain VIEW re-aggregating ~85k rows every read, ~51 GB I/O/day) + a heavier
cold start (57s) + reduced warm-keeping polls → cold-start retry death-spiral → Supabase I/O drained. **You rolled prod
back to v26.861** and fixed prod directly:
- **`vercel.json maxDuration` 60 → 300** (broke the retry loop).
- **`category_sales_summary` → MATERIALIZED VIEW** (read 13.3s → <1ms, hourly refresh).
- KV data-cache had shipped **behind a flag with no KV store provisioned → inert** (didn't help).

**Because of that, before promoting this package:**
1. **`vercel.json` in THIS package is now `maxDuration: 300`** (I raised it from 60 so a fresh deploy can't revert
   your prod fix). Confirm 300 lands.
2. **`category_sales_summary` matview:** this repo's `migrations/schema.sql` still defines it as a **plain view** — I
   did **not** author a matview migration (didn't want to conflict with the exact definition you applied on prod). Your
   prod matview is the source of truth; **ensure the deploy doesn't recreate it as a plain view.** Worth reconciling
   the repo to match prod when convenient.
3. **Provision + link the Vercel KV store** so `KV_REST_API_URL` / `KV_REST_API_TOKEN` are live (§3). The cache is the
   thing that stops every cold start re-pulling ~12 MB from Supabase — a flagged-off cache does not count as shipped.
4. **Cold-start budget:** this package adds several features to the boot/data build. Please measure cold start against
   the 300s ceiling before promoting (your release rule: don't promote if cold start > half the platform limit).

No new npm dependencies.
