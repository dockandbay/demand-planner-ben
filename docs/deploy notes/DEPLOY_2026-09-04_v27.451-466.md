## ⚠ CRITICAL FIX — FBA-transfer refusal latch (v27.466) — INCLUDED
**In this package** (`artifact_v16.7.html`, FBA-transfer block, ~18 lines). Three-part latch failure that closed into an **infinite refresh loop** for a read-only user:
1. `server.mjs` returns **403** for the FBA-transfer refresh when the signed-in email has no `supply_edit` (an email absent from `planner.app_permissions` is read-only everywhere).
2. The client did `.then(r => r.json())` then ran the success path — a 403 body is valid JSON, so a refusal looked identical to success. It never checked `r.ok`.
3. The success path calls `render()` → `_fbaTrfOnView()` → `_fbaTrfMaybeRefresh()`, which fires when `last_run` is > 1h old. Only the success handler stamps `last_run`, and the 403 blocked it, so the test stayed true forever (the in-flight `_fbaTrfBusy` guard was already cleared before `render()`).

**Fix:** a refusal now **latches `_fbaTrfBlocked`** and never reaches the success path, so `render()` is not called and the loop cannot close. It also catches the **200-with-`ok:false`** case (Cin7 not configured), which had the same stale-`last_run` problem. `_fbaTrfMaybeRefresh` no-ops while latched; a manual **⟳** clears the latch and retries; the box shows **⚠ not updating** with the reason rather than presenting stale in-flight data as fresh. Verified: `node`/vm syntax clean; driven in jsdom — 403 latches, `maybeRefresh` no-ops while latched (loop broken), manual retry clears it.
