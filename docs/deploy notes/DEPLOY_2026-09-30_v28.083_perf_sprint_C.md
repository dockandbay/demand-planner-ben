# v28.083 — Performance Sprint C: drawer, conditional GETs, SKU cache (30-Sep-2026)

Follows v28.081 (A) and v28.082 (B). Server only, **no migration, no env var, no product-logic change**.
All payloads byte-identical (verified: `po-detail` batched vs legacy on three live POs, diffed as JSON).

## What changed

- **PO drawer (`GET /api/supply/po-detail/:po`)**: the 20 per-PO lookups used to go out as 13 + 9 separate
  `pool.query()` calls in two `Promise.all` rounds. On the small pool that is ~6 queue waves × a pooler round
  trip; `HZ_QLOG` showed 300 to 700 ms of pure queue wait on trivial one-row SELECTs. Now the same statements
  go as **one multi-statement simple query** (`$1` bound as an escaped text literal, results parsed by pg with the
  same type parsers) while `poShipObj` and the memoised price-list index run alongside. If the batch fails for
  any reason (an optional table missing, an unusual PO ref) the legacy per-query path runs with its original
  per-query fallbacks. `HZ_PO_DETAIL_LEGACY=1` forces the legacy path for diagnostics.
  Measured: **0.35 s** (was 1.0 to 2.7 s).
- **Conditional GETs**: every gzipped JSON GET now carries a content `ETag` and, unless the route set its own
  `Cache-Control`, `private, no-cache` (stored by the browser, always revalidated, never served stale). A repeat
  fetch of an unchanged payload (order-plan 5 MB, purchase-orders 3 MB, skus, deposits…) is a **304 with no
  body**; the browser hands the cached JSON to `fetch()` as a normal 200. Routes that set `no-store` are unchanged.
- **`skus`** joins the section response cache (param-free, user-independent): 1.9 s live → ms warm.
- **`HZ_QLOG=<ms>`** (off by default): logs every DB query slower than `<ms>` as
  `[q 123ms] GET /api/... :: <sql head>` (route-attributed) for future diagnosis.

## Measured (sandbox)

| | before | after |
|---|---|---|
| PO drawer open | 1.0 to 2.7 s | 0.35 s |
| `skus` (Order plan) | 1.9 s | ~5 ms warm |
| Repeat fetch of an unchanged section | full body | 304, 0 bytes |

## Not done (deliberately)

Column projection on the PO grid: measured over the wire the grid is 179 KB gzipped (3 MB decoded); the cost was
the server build (fixed in Sprint A), not the wire. Trimming keys would risk the ~730 property reads in the client
for a small parse gain. Left as is.

## Prod notes (Diviyaj)

Nothing to apply beyond the pull. Multi-statement simple queries run fine through the transaction pooler (tested on
the Supabase 6543 pooler). If a proxy strips `ETag`, everything still works (full 200s as before).
