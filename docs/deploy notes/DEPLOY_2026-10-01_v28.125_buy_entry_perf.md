# v28.125: BUY / FBA entry no longer does redundant 3 s demand rebuilds (01-Oct-26)

**Branch:** `phase-2.1-suppliers` · **Live `/api/version` checked 01-Oct-26:** `v28.122.1`
**Files:** `artifact_v16.7.html`, `supply/inject.html`. No migration, no env vars, no server change.

## What we found (measured, jsdom on the served sandbox page)
Your read on SUPPLY to DEMAND/BUY was right that it's client-side, but the cost isn't `BUY_CACHE`:

| Step | Time |
|---|---|
| `buildLiveDemand()` (demand overlay rebuild) | **~2,900 ms** |
| Cold recompute of every SKU's buy qty (721 SKUs, UK) | 50 ms |
| Warm (cache hit) | 0.3 ms |
| BUY re-entry / BUY to FBA / FBA to BUY (no rebuild) | 8 to 11 ms |

So keeping `BUY_CACHE` across view switches would save ~40 ms and risk stale buy numbers (it has inputs outside its `sku|mkt` key: `plw`, `fbw`, `atr`, `AFTER20`, extra-stock pools). **Not done.** The seconds were two redundant overlay rebuilds:

1. **First BUY/FBA or DEMAND render after load rebuilt twice.** The one-time "PP cover" guard (`render()` in BP and in the demand plan) forced another `buildLiveDemand()` even when one had just finished, though every build already fills `PREPACK_COVER` from the server-injected `PREPACK_MAP`/`PREPACK_STOCK`. Now `buildLiveDemand()` marks the cover done when it completes with real SKU data.
2. **A backgrounded tab set `BUY_FC_STALE=true` on every server data change** (`inject.html` hidden-tab path), so the next BUY/FBA entry rebuilt the overlay. The bust only drops SUPPLY section data; demand inputs are client-held and unchanged, so the rebuild produced identical numbers (proven below). Removed.

**Latent bug fixed along the way:** in lazy-SKU mode (the default since v28.081) the loader never rebuilt the overlay after SKU data landed. If the initial build ran first (on empty maps), the buy overlay was only corrected by the redundant PP-guard rebuild, and never if a deployment had no prepacks. `lazyLoadSkuData()` now re-arms `DEMAND_BUILT` / `_PP_COVER_INIT` so exactly one rebuild happens on real data.

## Results

| Entry after a forecast edit (legit stale) | 3,067 ms | 2,765 ms (still rebuilds, correct) |

## Buy plan before/after (all 5 markets, 721 SKUs)
- Buy 3PL, urgent, Buy FBA, 3PL to FBA and Zalando transfers, future buys: **0 differing SKU rows** out of 415 with a buy (70,341 units).
- Rebuild from unchanged inputs vs the snapshot: identical in UK, US, EU, AU, CA.
- `PREPACK_COVER` populated (466 entries) with the guard set, lazy mode on.
