# Deploy note — Large-file uploads via Supabase Storage (v27.695)

## What changed
Any file upload over ~3MB now uploads **direct to Supabase Storage** from the browser (signed URL), instead of base64-through-the-serverless-function. This clears Vercel's ~4.5MB request-body cap that was silently failing large uploads on prod. Files ≤3MB are unchanged (still base64 → Postgres bytea). Covers every upload path in the app AND the supplier portal.

## Infra to set up on prod (Diviyaj)
1. **Create a private Storage bucket** named `horizon-uploads` on the prod Supabase project (`oolwklahstnvocaugryg`). Not public. Set the per-file size limit to **100MB** (matches the app's hard cap).
   - No RLS policies needed: the server mints signed upload/download URLs with the service-role key; access control stays in the app's existing auth (planner key for admin, magic-link for portal).
2. **Env vars** (server-side, preview + prod):
   - `SUPABASE_URL=https://oolwklahstnvocaugryg.supabase.co`
   - `SUPABASE_SERVICE_ROLE_KEY=<prod service_role secret>`  ← write-capable, keep out of git
   - `SUPABASE_STORAGE_BUCKET=horizon-uploads` (optional; this is the default)
   - If unset, the app still runs — large uploads return 503 ("storage not configured"); small uploads keep working.

## Migration
- `migrations/276_storage_paths.sql` — adds a nullable `storage_path text` to `portal_attachments`, `quality_docs`, `payment_remittances`, `product_specs`, `edi_project_files`, `tpl_invoice_files`, `xero_compare_snapshot`; relaxes NOT NULL on `edi_project_files.data`, `quality_docs.data`, `tpl_invoice_files.content` so a Storage-backed row can have null bytes. Idempotent, no backfill — existing rows keep their inline bytes and serve exactly as before.

## New endpoints
- `POST /api/storage/sign-upload` — admin app (planner-key gated)
- `POST /api/portal/storage/sign-upload` — supplier portal (magic-link gated)
Both return `{upload_url, storage_path, storage_sig}`; the client PUTs the file to `upload_url`, then posts `{storage_path, storage_sig, byte_size}` back to the normal upload endpoint. `storage_sig` is an HMAC (keyed off the service secret) so a client can't attach a forged path to a record.

## Behaviour notes
- Downloads of Storage-backed files 302-redirect to a short-lived signed URL (bytes skip the function both ways). Inline-rendered docs (spec sheets, portal attachments) keep rendering inline; the rest download as attachments — same as before.
- Fully backward-compatible: no data migration, old bytea rows untouched, buy plan unaffected.
