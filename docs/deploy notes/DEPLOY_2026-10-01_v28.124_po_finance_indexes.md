## How to apply (important)
- **Run with `psql -f` in autocommit (NO `-1`), or one statement at a time.** Sent as one multi-statement batch (Supabase SQL editor, or a runner that wraps in BEGIN/COMMIT), it fails with `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. Tested: that is exactly what happens.
- Re-runnable (IF NOT EXISTS). Tested twice on sandbox; the second pass is a no-op.
- **Interrupted build trap:** a failed CONCURRENTLY build leaves an INVALID index that IF NOT EXISTS then skips. Run the post-check at the bottom of the file; it must return 0 rows.
- The migration number assumes prod is at 320. Renumber if you've used 321.

## Size and write cost
- Sizes (measured on sandbox, prod row counts are within 5%): `ship_group_idx` **56 kB**, each `shipment_name` index **16 kB**. Under 100 kB in total.
- Build time: well under a second each at these sizes. CONCURRENTLY holds only a SHARE UPDATE EXCLUSIVE lock, so reads and writes keep flowing.
- Writes: one extra b-tree insert per inserted row, and per updated row only when the indexed columns change (otherwise updates can stay HOT). Measured: a full update of all 1,378 POs took 391 ms without the index and 350 ms with it, i.e. no difference beyond noise.
- The Flexport hourly rewrite: prod already has an `updated_at` index on both tables, so every synced row is already a non-HOT update. The new index adds about 546 tiny inserts per sync (sub-millisecond) and some bloat that autovacuum clears.
