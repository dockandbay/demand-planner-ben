# v28.089 — Broad response caching for heavy report endpoints (30-Sep-2026)

Perf (Ben: "find more areas where load is slow and we can fix with cache — seems to be a lot"). `server.mjs` only,
**no migration, no env var, no product-logic change**. Same pattern as the section cache; cached bytes are captured
from the live handler, so responses are identical.

## Method

Profiled every hot-path GET endpoint (supply / bi / demand / kpi / scenario / product) cold vs warm. "Warm ≈ cold"
means uncached-and-slow. Cached the clearly param-free, user-independent ones.

## Two additions

**1. More `/api/supply/:section` cases** joined `SECTION_CACHE_TTL_MAP`:
`shipment-plan` (1.3 s), `pipeline` (0.9 s), `upcoming` (1.6 s), `suppliers` (0.8 s), `products-all` (2.5 s).

**2. A general response-cache middleware** (`RESP_CACHE`) extends the identical epoch-gated, lazy-capture, TTL pattern
to standalone report routes (cached only when there are **no query params** — filtered variants always run live):

Supply-domain entries use a 10-min TTL and are **epoch-gated** (any supply edit busts them). The four demand/kpi
analysis reads use a **90-s TTL** (no supply-epoch link, so a forecast edit shows fresh within ~90 s). Registered
after the auth gate, before the API routes, so it wraps them; skips any request with query params.
