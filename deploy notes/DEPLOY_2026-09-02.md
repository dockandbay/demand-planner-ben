## v27.360 — Order Plan "Country risk" fix
A discontinued-but-previously-released SKU (e.g. `PICNIC-DES-LG-SPRCLUB` on a **US** PO) was wrongly flagged
**Country risk**. Root cause: `not_avail_market` used `v_product_availability.is_available`, which bakes in the
discontinue date, so a released-then-discontinued SKU looked "never released". Both `not_avail_market` subqueries now
use **`available_no_disc`** (raw channel flag, ignoring discontinue) → Country risk only fires for SKUs genuinely never
released in the market; a released-but-discontinued SKU trips the separate **Discontinued** flag instead.
- **Depends on mig 250 (`available_no_disc`)** — **already live** (you applied it 01-Sep), so this is code-only.
- Verified in sandbox: PICNIC US country-risk TRUE→FALSE; a never-released US SKU stays TRUE. `/api/supply/order-plan-exceptions` 200.

## v27.361 — DB perf/stability (your 01-Sep brief; server-only)

**TASK 1 — `queryCapped` is serverless-safe.** Removed the `BEGIN READ ONLY … SET LOCAL … COMMIT` transaction; it's now
a thin autocommit `pool.query()`. The **transaction** (not the timeout) was what stranded pooled connections on frozen
containers (~1,128 idle-in-transaction reaps/day). Autocommit single statements can't strand a connection. Signature
unchanged — all ~14 call sites untouched.
- Runaway cap moved to pool `options: '-c statement_timeout=30000'`.
  ⚠ **Verify on live:** the **sandbox session-pooler silently IGNORES `options`** (I tested — `SHOW statement_timeout`
  stayed 2min, `pg_sleep(35)` ran uncapped). Supavisor should forward startup options, but please confirm
  `SHOW statement_timeout` = 30s on a live pooled connection. If it isn't honored, set it role-level
  (`ALTER ROLE … SET statement_timeout='30s'`, pooler-agnostic). **The reap fix is independent of the cap and holds either way.**
- The DB-level 60s `idle_in_transaction_session_timeout` backstop is untouched.

**TASK 2 — cache warmers/timers guarded with `!process.env.VERCEL`.** `makeCache` (boot-warm + re-warm timer), the
Actions cache (boot-warm + 10-min timer), and `_oaRefresh` (warm + timer) no longer fire on Vercel; each builds lazily
on first request. On a frozen/idle container these fired the builder (opening a pooled backend) with no request in
flight → the overnight reap spike. **Live data confirms the lever:** the dominant PO-finance query ran
**12,405×/13 days ≈ 954/day = the exact daily cold-start count** — an unguarded boot-warm on every container. This
removes them.

**TASK 3 — measured, deliberately NOT blanket-applied.** `pg_stat_statements` shows the 83.8% query is the shared
`poRowsCache` (`FROM mastered calc4 ORDER BY po`) — a **full-history** consumer: it feeds recent-complete POs (above
the archive cutoff), the `?includeArchived` reveal, AND the payments-overdue nav badge (unpaid milestones across all
POs). A `NOT complete` filter would drop needed rows / undercount the badge — and your rule was "leave full-history
consumers unchanged." TASK 2 already removes this query's call multiplier. If per-call 2.9s still bites after 1+2 land,
the safe win is a small refactor (push the **archive** filter into the cached build + a live `includeArchived` path +
a separate badge query) — flagged, not shipped blind.

**FYI (not changed):** `processPaymentEmails` (30s email worker) is also an unguarded timer, but it's pure autocommit
→ **not** a reap source. Guarding it needs a cron trigger to replace the worker (your infra call).
