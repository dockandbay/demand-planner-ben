## Logic

### 🟠 MODERATE — ZAL forecast edits don't reach the buy plan until page reload (3a↔3b gap)
The demand grid reads the ZAL forecast **live** (`IV`/`forecast_inputs/outputs`), but the buy feed's Zalando overlay (`buildLiveDemand` "2c") reads the **page-load `ZAL_FC` global**. So if a planner edits a ZAL cell, saves, and looks at the buy **without reloading**, Buy 3PL still uses the old Zalando number. Every *other* channel flows to the buy live. This is exactly what **Stage 3b** (point the buy feed at the cascade) closes — currently deferred as buy-plan-critical.
- **Impact:** stale-until-reload ZAL buy contribution. Not wrong after a reload.
- **Options:** (a) accept + document (reload to see buy impact); (b) small client patch — refresh the `ZAL_FC` global from saved values after a ZAL save; (c) do Stage 3b properly (snapshot-gated). → **Question 1.**

### 🟡 LOW — `chKey` "default-to-`'b'`" (tech debt)
`ch==='DTC'?'d':…:ch==='ZAL'?'z':'b'` — any *unrecognised* channel silently maps to B2B, now in ~9 copies. Correct today; a future channel added *outside* the modular refactor would mis-map silently. Modular Phase 2 (parked) replaces these with a `CHANNELS`-driven lookup.

### 🟡 LOW — received-POs endpoint is unauthenticated
`POST /api/supply/received-pos/process` is open (n8n system trigger). It only acts on rows n8n wrote and is idempotent, so the blast radius is nil — but on live anyone could trigger a processing pass. **Recommend a shared-secret header** (env var) checked in the handler for the live wiring. → **Question 2.**

### 🟡 LOW — auto-complete timeline note may ping the ✉ bell
The received-POs processor writes an internal `supplier_notes` note ("📦 Received…"). The top-bar timeline-notifications bell reads `supplier_notes`; system auto-complete notes could add noise there. → **Question 3.**

### ✅ Confirmed clean
- **No Zalando double-count:** `dem.ZAL` is written only by the "2c" overlay; `buildLiveDemand` section-2 cascade iterates DTC/B2B/FBA only, so ZAL never doubles. ZAL sales actuals feed display (`ga`/`DATA`) but not the buy's `dem.ZAL`.
- **received-POs paths:** already-COMPLETE / PO-not-found → no action; idempotent via `processed_at`; duplicate feed rows for one PO are harmless (2nd sees COMPLETE).
- **Modular P1 inert:** nothing in the demand/buy logic reads `CHANNELS`; seeded to mirror current behaviour exactly.
- **ZAL LY actuals:** flow via the `category_sales_summary` VIEW + unfiltered SKU feed; forecast months stay absolute manual.

## Performance

### 🟡 LOW–MOD — `ZAL_FC` derived on every `/` request
Stage 2 derives `ZAL_FC` by scanning **all** `FC_OUTPUTS` keys (~10k+) on each page serve (outside the SWR data cache). Cheap per key but on the hot serve path. **Fold the derivation into `_dataCache`** (compute once per cache refresh). Low effort.

### 🟡 LOW–MOD — `renderBuyMoveActions` transfer computation
Adds ~`vis × (markets−1) × 2` `trfLane` calls (≈ tens of thousands across 5 markets) on top of the existing ~3,500 `getBuyQtys`. Actions is an on-demand tab (not hot) and `getBuyQtys`/`project` dominate, so it's a modest increment — but if the Actions tab feels slow, skip SKUs with no `TRANSFER_LEADS` lane before calling `trfLane`.

### 🟢 LOW — `zalInit()` runs every `renderMain`
Idempotent but re-scans `ZAL_SKUS` (84) + `DATA.some/find` per ZAL subcat (~3× a 500-row scan) on every render/filter/toggle. Negligible in practice; a one-shot `_zalWired` flag (reset on lazy SKU-load) would remove the repeat.

### 🟢 LOW — misc
`buildZalSkus`/`buildZalStock`/`buildChannels`/`buildCountries` add a few small queries per page load (injected globals) — fine. received-POs processor does per-row queries — fine for a low-volume feed.
