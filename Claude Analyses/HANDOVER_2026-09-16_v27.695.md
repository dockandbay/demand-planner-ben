## PRIMARY WORKSTREAM — Large-file uploads via Supabase Storage (v27.695)

### The ask (Ben, verbatim)
> "Anything over 4mb needs this method. On both supplier portal and horizon admin side. Any upload file method anywhere on entire app. You can proceed"

Earlier context: "Is there any way to allow larger files like 30 megabytes to be uploaded through front end. Vercel has limitation?" → then "I mean can supabase handle it". (He ruled out Fulfil and Dropbox-login flows.)

### Why
Every upload was sent as **base64 inside a JSON body → through the Vercel function → stored as Postgres bytea**. Base64 inflates ~33% and **Vercel caps the serverless request body at ~4.5MB**, so any file over ~3.3MB silently failed on prod. The `express.json({limit:'25mb'})` at `server.mjs:725` only ever helped local/self-hosted.

### The design (what was built)
Files **≤3MB** keep the inline base64→bytea path **unchanged**. Files **>3MB** upload **direct to Supabase Storage** from the browser via a signed URL (bytes never touch the function). Threshold is **3MB not 4** deliberately: base64 of a 4MB file = 5.3MB payload, already over Vercel's cap; 3MB raw → ~4MB payload, safely under.

**Storage backend:** one **private** bucket `horizon-uploads`, foldered by category (`product-docs/`, `specs/`, `samples/`, `quality/`, `edi/`, `portal/`, `timeline/`, `tpl/`, `inventory/`, `zalando/`, `klaviyo/`, `invoice/`, `remittance/`, `po/`, `xero/`, `product-dim/`). Downloads of Storage-backed rows **302-redirect to a short-lived signed URL** (bytes skip the function both ways). Old bytea rows are untouched and serve exactly as before — **no data migration**.

### Server side (`server.mjs`, all done + committed)
- **Config + helpers** inserted right after `app.use(express.json…)` (~line 726 onward):
  - `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `STORAGE_BUCKET` (default `horizon-uploads`), `STORAGE_ENABLED`, `STORAGE_INLINE_MAX = 3MB`, `STORAGE_MAX = 100MB`.
  - `storageSignUpload(path)`, `storageSignDownload(path,{expiresIn,filename})`, `storageDelete(path)`, `storageFetch(path)` — plain `fetch()` against Storage REST API, **no `@supabase/supabase-js` dependency**.
  - `storageKey(category,filename)` → `<cat>/<yyyy-mm>/<uuid>-<safe filename>` (server-controlled; client never picks the path).
  - `storageSig(path)` / `storageSigOk(path,sig)` — **HMAC** keyed off a sha256 of the service secret. Stops a client attaching a **forged/other-tenant** storage path to a record (matters for the multi-tenant portal).
  - `resolveUpload(body,{base64Field,maxInline})` → `{storagePath, buf, byteSize}` (exactly one of storagePath/buf set); throws `{status,message}`. Used by **storing** endpoints.
  - `resolveUploadBytes(body,opt)` → async Buffer (inline or fetched from Storage). Used by **parse-only** endpoints.
  - `serveStored(res,row,{filename,mime})` → 302 to signed URL if `row.storage_path`, else streams `row.data`. Used by **download** endpoints.
- **Sign endpoints** (~line 815-819):
  - `POST /api/storage/sign-upload` — admin app (planner-key/cookie gated by Gate 1).
  - `POST /api/portal/storage/sign-upload` — supplier portal, `portalAuth` guarded. **This exists because suppliers have no planner key** — a portal call to the plain `/api/storage/sign-upload` would be 401'd by Gate 1 (line ~859). Both share `signUploadHandler`.
- **~40 endpoints converted** (a fork did the mechanical pass): every storing endpoint now accepts `storage_path` OR inline base64 (`resolveUpload`), every download uses `serveStored`/signed-redirect, every parse-only uses `resolveUploadBytes`. Inline caps raised to **20MB**; the 100MB hard ceiling is enforced in `sign-upload`.

### Client side (all done + committed)
Shared helper **`hzUpload(file,{field,category,signUrl})`** — a self-contained ES5 function copied verbatim into three shells:
- `supply/inject.html` (~line 851, inside the main IIFE)
- `supply/portal-view.js` (~line 845)
- `artifact_v16.7.html` (~line 1037, top-level script scope)

It returns an object to spread into the POST body: `{filename,mime,byte_size}` plus either `{<field>:b64}` (≤3MB) or `{storage_path,storage_sig}` (>3MB → signs, PUTs to Storage). Every ~30 upload call site was routed through it.

**Sign-URL wiring:** `portal.html` EP map (~line 91) has `signUpload:'/api/portal/storage/sign-upload'`; `inject.html` preview-as-supplier `ep:` map (~line 7817) has `signUpload:'/api/storage/sign-upload'`; `portal-view.js` passes `signUrl:(EP.signUpload||'/api/storage/sign-upload')`.

**Contract change:** the timeline widget's `uploadAll` went from `opts.upload(f, b64, cb)` to `opts.upload(f, fields, cb)` in both `inject.html` and `portal-view.js`; `hzTlUploader` now builds `Object.assign({kind,ref},fields,extra)`. The only uploader passed to `hzTlAttach` is `hzTlUploader` (grep-verified), so no other caller changed. Timeline per-file cap raised 4MB → 100MB.
